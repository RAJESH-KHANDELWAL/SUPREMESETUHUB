# GLOBAL STORAGE ECOSYSTEM

The STORAGE layer owns the provider-neutral storage runtime, provider selection, object lifecycle boundary, category namespaces, and provider catalog. It does not own API authentication or duplicate the central asset metadata/ACL engine.

## Runtime architecture

- Asset identity, ownership, access grants, links, soft-delete, restore, and audit remain in `backend/engine/storage/`.
- Physical bytes are handled by existing adapters in `backend/storage/filesystem.py` and `backend/storage/s3.py`.
- `provider_runtime.py` selects the configured physical backend and provides a common stream upload, open, existence, delete, and health interface. Health reports write verification separately; it does not claim read verification unless an independent read-back test is added.
- Authenticated HTTP endpoints remain in `backend/api/storage_routes.py`; they delegate physical I/O to the STORAGE runtime and asset metadata/permissions to StorageEngine.
- Provider and category catalogs remain discovery metadata. A catalog entry is not a working connector.

## Implemented physical providers

| Provider ID | Adapter | Status |
|---|---|---|
| `local` | LocalFileStorage | Implemented; requires `SUPREME_FILE_STORAGE_DIR` |
| `aws_s3` | S3ObjectStorage | Implemented; requires `AWS_S3_BUCKET`, AWS SDK and authorized AWS credentials |

Select with `SUPREME_STORAGE_PROVIDER=local` or `SUPREME_STORAGE_PROVIDER=aws_s3`. Local storage on ephemeral hosts is not durable unless a persistent volume is mounted and configured. S3 health performs a bucket check and temporary write/delete probe.

Adobe, Google Drive, OneDrive, MEGA, Proton Drive and other catalog providers are not falsely reported as connected. They need their own documented authorization flows and provider-specific storage adapters before activation. Adobe API credentials/readiness do not by themselves implement Adobe Storage operations.

## API endpoints

- `GET /api/v1/storage/ecosystem/status`
- `GET /api/v1/storage/ecosystem/providers`
- `GET /api/v1/storage/health`
- `GET /api/v1/storage/configuration`
- Existing authenticated upload, asset metadata, and download endpoints continue to use the central StorageEngine.

## Security and ownership

- API routes require the existing authenticated user dependency.
- StorageEngine remains the source of truth for asset owner, permissions, and audit.
- Object keys are generated by the server and partitioned by owner and area.
- Provider credentials are read from the host environment/secret manager; never commit secrets.
- Physical storage status is reported separately from metadata database readiness.
- Downloads resolve the provider recorded in each asset's metadata, so changing the selected provider does not silently redirect old objects.
